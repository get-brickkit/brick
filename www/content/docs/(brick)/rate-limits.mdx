---
title: Rate Limits
description: Refuse calls over a limit per IP, per caller or per any key you choose, with rateLimit on the action.
---

`rateLimit` on an action caps how often it runs: at most `max` calls per `windowMs` milliseconds, per key. A call over the limit is refused with `RATE_LIMITED` (HTTP 429) before `authorize` and `execute` run.

```ts title="src/services/auth/actions/login.action.ts"
import { t } from "@brickkit/core";
import { auth } from "../auth.service";

export default auth.action({
  name: "login",
  input: t.Object({ email: t.String(), password: t.String() }),
  rateLimit: [
    { per: "ip", max: 20, windowMs: 60_000 },
    {
      per: ({ input }) => input.email.toLowerCase(),
      max: 5,
      windowMs: 15 * 60_000,
    },
  ],
  execute: async ({ input, ctx }) => {
    // ...check the password
  },
});
```

Each address may try 20 times a minute, and each email 5 times in 15 minutes, whoever sends it.

`rateLimit` takes one limit or a list. It works on every kind of action: `service.action`, `defineAction`, `resource.action`, `resource.command` and tools.

## The counter needs a storage

Brick counts in the service's [key-value storage](/docs/storage), so every process of the app shares the count:

```ts title="src/services/auth/auth.service.ts"
import { defineService, defineStorage, redis } from "@brickkit/core";

export const auth = defineService("auth", {
  deps: { cache: defineStorage({ driver: redis() }) },
});
```

An action that declares `rateLimit` on a service without one fails at startup, naming the service and the action. Brick never counts in memory because nothing was configured.

## Keys: `per`

| `per`                        | Counts together                                                                                                                                                                       |
| :--------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `"ip"`                       | Calls from one client address. A call without an address (in-process, or a test through `app.handle`) skips this limit.                                                               |
| `"actor"`                    | Calls from one caller, by the `id` the service's [`identity`](/docs/context) hook returns. An anonymous caller counts by IP, so the limit is never skipped where there is an address. |
| `({ input, ctx }) => string` | Calls with the same key. `input` is validated and typed from the action's schema. Return `null` or `undefined` to skip this limit for the call.                                       |

A service that limits any action `per: "actor"` must declare `identity`, or it fails at startup:

```ts title="src/services/crm/crm.service.ts"
export const crm = defineService("crm", {
  deps: { cache },
  context: async ({ request }) => ({ user: await readSession(request) }),
  identity: (ctx) => ctx.user && { id: ctx.user.id },
});

export const exportContacts = crm.action({
  name: "exportContacts",
  authorize: ({ user }) => !!user,
  rateLimit: { per: "actor", max: 3, windowMs: 3_600_000 },
  execute,
});
```

Keys are opaque strings. Each action, each limit in its list and each kind of key has its own counter, so a key that contains separators or newlines never reaches another's count, and a user whose id looks like an address is not counted with that address.

## When a call counts

The limit runs after input validation and before `authorize`:

- An input that fails validation (400) does not count.
- A call that `authorize` refuses (401 or 403) does count, so guessing a password or a token is limited too.
- The limits of a list are counted in order, and the first one over its `max` refuses the call. The limits after it are not counted for that call.

Each limit is a fixed window: the counter starts with the first call and resets `windowMs` later.

In-process calls (`action.run`, `useService`) go through the same stage, so `per: "actor"` and custom keys count there too. An action without `rateLimit` costs nothing; an action with one always answers asynchronously.

## The response

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 42
Content-Type: application/json

{
  "name": "ActionExecutionError",
  "code": "RATE_LIMITED",
  "message": "Too many calls to 'login'; retry in 42 s",
  "status": 429,
  "details": { "retryAfterSeconds": 42 },
  "requestId": "…"
}
```

`Retry-After` is in whole seconds, and at least 1. In-process, the same `ActionExecutionError` is thrown. `RATE_LIMITED` is a standard error code, so the [typed client](/docs/typed-client) knows it, and an action can refuse a call itself with `error.RATE_LIMITED(message, { retryAfterSeconds })`, which sets `Retry-After` the same way.

OpenAPI lists a 429 response with its `Retry-After` header on every limited action, and `introspect()` shows each limit's `max` and `windowMs`.

## Behind a proxy

The client address is the peer of the TCP connection. Brick never reads `X-Forwarded-For` or any other header itself, because any client can send them. Behind a proxy, every call would come from the proxy's address, so tell Brick where your proxy puts the client's:

```ts title="src/app.ts"
export default brick({
  services: [auth, crm],
  clientIp: ({ request, peer }) => request.headers.get("fly-client-ip") ?? peer,
});
```

`clientIp` receives the request and the peer address (`undefined` without one), and returns the address to count by. Read only a header your proxy sets and overwrites; a header the client could set lets it pick a fresh key on every call.

## When Redis is down

When the storage rejects with `StorageUnavailableError`, the call is neither failed nor let through unlimited: Brick counts it in the process's memory instead, and logs one warning when that starts and one when Redis is back. During an outage the limits hold per process, not across processes: with four processes, a caller can make up to four times `max` calls. The count starts over in memory when the outage starts, and continues from Redis's count when it ends.

Any other storage error fails the call with a 500.

## Testing

Give the service a `memory()` storage in tests, or swap it for one call through its deps:

```ts title="src/services/auth/actions/login.test.ts"
import { defineStorage, memory } from "@brickkit/core";

const cache = defineStorage({ driver: memory() });
await login.run({ email: "a@b.c", password: "x" }, { deps: { cache } });
```

A fresh storage per test starts every count at zero.

`per: "ip"` needs a client address. `createTestApp` and `app.handle` call the app without a server, so there is no peer and the limit is skipped; a test that checks an IP limit listens on a port and calls it with `fetch`, where the peer is `127.0.0.1` or `::1`:

```ts
const app = brick({ services: [auth] });
app.listen(0);
const call = () =>
  fetch(`http://localhost:${app.server!.port}/api/auth/login`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ email: "a@b.c", password: "x" }),
  });
// ...
await app.stop(true);
```

With `clientIp`, `app.handle` sees the address it returns, so a test can send the proxy's header instead.

## Lint

The `public-rate-limit` rule of [`brick lint`](/docs/brick-cli/lint) warns on an action, command or tool that anyone may call (no `authorize`, and no `access` or `access: "public"`) and has no `rateLimit`.
