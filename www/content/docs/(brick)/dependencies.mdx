---
title: Dependencies & Service References
description: Give a service the clients it uses with defineService({ deps }), and call other services with useService.
---

A service holds the things its code uses from the outside, such as a shipping carrier, a mailer or a payment client, as `deps`. Each service sees only its own. Tests swap in fakes.

## Service deps

```ts title="src/services/orders/orders.service.ts"
import { defineService } from "@brickkit/core";
import { createCarrier } from "../../carrier";

export const orders = defineService("orders", {
  database,
  deps: { carrier: createCarrier() },
});
```

```ts title="src/app.ts"
import { brick } from "@brickkit/core";

export default brick({ services: [orders] });
```

`deps` holds real values, as a plain object of values by name. A class instance or a `Map` is refused at startup. `ctx.deps` is typed from that object, so there is nothing to declare twice. A dep set to `undefined` fails at startup: `Service "orders": dep "carrier" is undefined; pass a value or leave it out`.

A [storage](/docs/storage) from `defineStorage` is a dep like any other: `deps: { cache }`, read as `ctx.deps.cache`. A [file storage](/docs/files) is read the same way, scoped to the caller's tenant for each call.

### When deps are created

A dep is created when the service module is imported, not when the app starts. `brick info` and `brick gen` import the app to read its services without starting it, so a dep's constructor runs there too. Open connections on first use, not in the constructor:

```ts
export function createCarrier(): Carrier {
  let client: CarrierClient | undefined;
  return {
    book: async (orderId) => {
      client ??= await CarrierClient.connect(); // first use, not at import
      return client.book(orderId);
    },
  };
}
```

### Reading deps

Actions, resource actions, commands, tools and socket handlers read their service's deps from `ctx.deps`:

```ts
orders.action({
  name: "book",
  input: t.Object({ orderId: t.String() }),
  output: t.Object({ trackingId: t.String() }),
  execute: async ({ input, ctx }) => ({
    trackingId: await ctx.deps.carrier.book(input.orderId),
  }),
});
```

`ctx.deps` holds only the service's own deps; a service without `deps` has an empty `ctx.deps`. An in-process call to another service runs with that service's deps, never the caller's.

### Listeners, schedules and workflow steps

Listeners and schedules belong to the app, not to a service, and a workflow step is a plain function the Workflow SDK calls by name, so it can't close over the service that started it. They call `useDeps(service)`, which returns that service's deps, typed from it:

```ts title="src/services/orders/workflows/fulfil-order.workflow.ts"
import { useDeps } from "@brickkit/core";
import { orders } from "../orders.service";

async function bookCarrier(orderId: string) {
  "use step";
  return useDeps(orders).carrier.book(orderId);
}
```

This replaces module-level singletons such as a `setOrdersContext()` that the app calls at startup, which the `no-global-context` lint rule reports.

When the code can't import the service, because a factory builds it (as `createOrdersApp` does in the events example), call `useDeps()` with no argument and give the type. In a listener, schedule or step of the app it returns the deps of every service of the app, by name; in one a [plugin](/docs/plugins/build-plugin#dependencies) adds, the plugin's deps:

```ts
useDeps<{ carrier: Carrier }>().carrier.book(orderId);
```

The type is not checked. When two services give the same name different values, that name has no single answer: spreading the result leaves it out, and reading it throws:

```txt
useDeps().carrier is ambiguous: services "orders" and "returns" both declare dep "carrier" with different values. Call useDeps(service) with the service you mean.
```

`useDeps()` with no argument throws when called outside a listener, a schedule or a step of a running app.

### Testing

Call an action directly with deps in the call context. They replace the service's deps of the same name; the others stay:

```ts
await bookAction.execute({
  input: { orderId: "o1" },
  ctx: { deps: { carrier: fakeCarrier() } },
});
```

Only deps the test writes do this. Deps that Brick gave a context, such as the `ctx` of a calling action or a spread copy of that `ctx`, never pass on: the called action runs with its own service's deps. A copy you make of the deps object itself (`{ ...ctx.deps }`) is a new object, so it does count as written by you.

The fake applies to the action you call and to actions of the same service that it calls with its `ctx`. It does not apply when the call leaves the service and comes back, or when you add `deps` to a `ctx` that a service has already resolved: the real dep runs in both cases. A test's deps given to a plugin's action replace the plugin's deps for that action only. To run a whole app on fakes, build the service in a factory that takes them, as `createOrdersApp({ carrier })` does in the events example.

### Plugins

A plugin declares its own `deps`, and the user passes them when installing it: `orders.use(notify({}, { deps: { mailer } }))`. The plugin's actions read those as `ctx.deps`, not the service's. See [Build a plugin](/docs/plugins/build-plugin#dependencies).

### Migrating from 0.15

`port<T>()`, `Ports`, `DepsOf` and the `deps` option of `brick()` were removed in 0.16. Move each value into the service that uses it, and pass `useDeps()` the service instead of the ports:

```ts
// Before (0.15)
export const ordersDeps = { carrier: port<Carrier>() };
export const orders = defineService("orders", { database, deps: ordersDeps });
export default brick({
  services: [orders],
  deps: { carrier: createCarrier() },
});
useDeps(ordersDeps).carrier; // in a step

// After (0.16)
export const orders = defineService("orders", {
  database,
  deps: { carrier: createCarrier() },
});
export default brick({ services: [orders] });
useDeps(orders).carrier; // in a step
```

`brick({ deps })` now fails at startup: `Brick: brick({ deps }) was removed in 0.16. Move each value into the service that uses it: defineService(name, { deps: { ... } })`. A plugin declares its deps with a placeholder of each type instead of `port<T>()`: `deps: { mailer: {} as Mailer }`. In a direct call, `ctx.deps` now replaces the service's deps per name; before, an app's deps won.

## Service references

`useService` calls another service's actions in-process, typed from that service:

```ts title="src/services/orders/actions/checkout.action.ts"
import { useService } from "@brickkit/core";
import { billing as billingService } from "../../billing/billing.service";

const billing = useService(billingService, { from: "orders" });

export default orders.action({
  name: "checkout",
  input: t.Object({ orderId: t.String(), amountCents: t.Integer() }),
  output: t.Object({ ok: t.Boolean() }),
  execute: async ({ input }) => {
    await billing.charge({
      orderId: input.orderId,
      amountCents: input.amountCents,
    });
    // A resource's actions sit under the resource: POST /api/billing/invoice/:id/send
    await billing.invoice.send({ id: input.orderId });
    return { ok: true };
  },
});
```

Each method takes the action's input, and optionally a call context (`{ traceId, user, tenantId }`). The call runs through the target's validation and authorization, with the target's own database, context and deps, and shows as an `rpc` span in the trace. `from` becomes `ctx.caller` in the target and can't be spoofed by the call context. See [Context isolation](/docs/context#context-isolation-across-in-process-service-calls).

The types come from the generated contract, `_brick/contract.ts`, which `brick dev` and `brick gen client` keep current. Renaming an action or changing its input becomes a compile error at every caller once the contract is regenerated. The contract must be part of the server's TypeScript program (include `_brick` in `tsconfig.json`). Until the contract describes the service, `useService` returns an untyped client.

### Migrating from `createServiceProxy`

`createServiceProxy` was removed in v0.11. Use `useService`, which is typed from the service instead of by hand:

```ts
// Before
const billing = createServiceProxy<{
  charge(input: { orderId: string; amountCents: number }): Promise<void>;
}>("billing", { from: "orders" });

// After
const billing = useService(billingService, { from: "orders" });
```
