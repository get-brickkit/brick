Brick-TS provides first-class support for AI agents through Model Context Protocol (MCP) tool declarations and JSON-RPC transports.

## Minimal Example

Define an AI tool on a service, then let `brick({ mcp })` serve every tool over MCP:

```ts title="src/services/documents.ts"
import { brick, defineService, t } from "@brickkit/core";

export const docsService = defineService("docs");

// 1. Declare an AI tool with an object input schema and description
export const searchDocs = docsService.tool({
  name: "search_docs",
  description: "Search knowledge base documents by query string",
  input: t.Object({
    query: t.String({ description: "Search terms or keywords" }),
    limit: t.Optional(t.Number({ default: 5 })),
  }),
  output: t.Array(
    t.Object({
      id: t.String(),
      title: t.String(),
      snippet: t.String(),
    }),
  ),
  execute: async ({ input, ctx }) => {
    return [
      {
        id: "doc_1",
        title: "Architecture",
        snippet: "Brick-TS is built on Bun...",
      },
    ];
  },
});

// 2. Serve every service tool at POST /mcp
const app = brick({ services: [docsService], mcp: true });
app.listen(4000);
```

## Serving MCP (`brick({ mcp })`)

`mcp: true` (or an options object) mounts an MCP endpoint that serves every tool the app's services register with `service.tool()`. It speaks the streamable HTTP transport statelessly: each `POST` gets one JSON response, and a `GET` that passes `authorize` answers `405` because the server opens no event stream. The server reports the app's `title` and `version` as its name and version.

| Option      | Default  | Description                                                                                                  |
| :---------- | :------- | :----------------------------------------------------------------------------------------------------------- |
| `path`      | `"/mcp"` | Where the endpoint is served.                                                                                |
| `authorize` | none     | `({ request, user }) => boolean \| Response \| void`, run on every MCP request after `auth.resolve` (below). |

`authorize` sees the principal [`auth.resolve`](/docs/access-control#signing-users-in) returned as `user` (`null` when there is none). Return `false` to answer `401`, or a `Response` to answer with it; anything else lets the request through. Each tool still runs its own `authorize` with `ctx.user` set to that principal.

```ts title="src/app.ts"
export default brick({
  services: [docsService],
  auth: { resolve: (request) => verifyToken(request) },
  mcp: {
    // MCP clients start OAuth from this challenge (RFC 9728).
    authorize: ({ user }) =>
      user != null ||
      new Response(null, {
        status: 401,
        headers: {
          "WWW-Authenticate": `Bearer resource_metadata="https://api.example.com/.well-known/oauth-protected-resource"`,
        },
      }),
  },
});
```

Serve the protected-resource metadata document from `auth.handler`, next to your provider's routes. The Pages example does this with Better Auth's MCP plugin: see `examples/pages/src/api/auth/brick.ts`.

### Output schemas

`tools/list` gives each tool with an `output` schema an `outputSchema`, and `tools/call` returns the result as `structuredContent` as well as text. MCP requires an object schema, so a tool whose output is a string, array or union is described as `{ result: <schema> }` and returns `{ result: value }`.

## Tools (`defineTool` / `service.tool`)

Tools are specialized actions designed for invocation by Large Language Models:

- **Object Schema Requirement**: The `input` schema, if present, must be a TypeBox object (`t.Object(...)`). Any other schema makes `defineTool()` / `service.tool()` throw `Tool '<name>' input must be an object schema` when the tool is defined.
- **MCP-only by default**: Tools are not mounted as HTTP routes. Set `http: true` on the tool (or register it with `service.action(tool)`) to also expose it as an HTTP action and in OpenAPI.
- **Agent Descriptions**: Provide clear `description` strings on the tool and each schema property; LLM agents use these descriptions to determine tool calling logic.
- **Annotations**: Tools accept MCP annotations: `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`. You can also set a top-level `title`:

```ts title="src/services/admin.ts"
export const deleteUserTool = adminService.tool({
  name: "delete_user",
  description: "Permanently delete a user account and associated data",
  annotations: {
    destructiveHint: true,
    readOnlyHint: false,
  },
  input: t.Object({
    userId: t.String({
      description: "The unique identifier of the user to remove",
    }),
  }),
  output: t.Object({ success: t.Boolean() }),
  execute: async ({ input, error }) => {
    return { success: true };
  },
});
```

## MCP Registry (`createMcpRegistry`)

`createMcpRegistry` gathers only explicitly defined tools:

- Standard service actions and internal functions are **never exposed** to AI agents unless declared as tools via `service.tool` or `defineTool`.
- You can pass `services` (their `service.tool()` tools are collected), standalone `tools` from `defineTool()`, or both.
- Two different tools with the same name are rejected with `Duplicate MCP tool: <name>` when the registry is created.

```ts title="src/mcp-setup.ts"
import { createMcpRegistry } from "@brickkit/core";
import { docsService } from "./services/documents";
import { adminService } from "./services/admin";

export const registry = createMcpRegistry({
  services: [docsService, adminService],
});

// Inspect available tools:
const toolList = registry.listTools();
console.log(toolList.map((t) => t.name)); // ["search_docs", "delete_user"]
```

## JSON-RPC 2.0 Handler (`createMcpHandler`)

`brick({ mcp })` uses this handler. Reach for it directly only to mount MCP somewhere `brick()` doesn't, such as another server. `createMcpHandler({ registry, serverInfo, protocolVersions? })` returns a stateless `(request, ctx?) => Promise<Response>` handler for MCP JSON-RPC 2.0 over HTTP POST. Non-POST requests get `405`, and notifications (requests without an `id`) get `202` with no body. It handles:

- `initialize`: Returns `{ capabilities: { tools: {} }, protocolVersion, serverInfo }`. The client's requested version is echoed if it is in `protocolVersions` (default `["2025-06-18"]`); otherwise the first listed version is returned.
- `ping`: Returns `{}`.
- `tools/list`: Returns each tool's `name`, `title` (if set), `description`, `inputSchema`, `outputSchema` (if it has an `output`), and `annotations`.
- `tools/call`: Validates and executes the tool, returning `{ content: [{ type: "text", text }] }`, plus `structuredContent` when the tool has an `output`. Strings are returned as-is; other values are JSON-stringified. A thrown error becomes a result with `isError: true` and the error message as text. An unknown tool name returns JSON-RPC error `-32602`.

The handler alone performs no authentication. Wrap it with your own auth, and pass an optional `ctx` (for example `{ user }`) as the second argument; it is forwarded to the tool's execution context along with the `request`.

### Connecting a Client

Point an MCP client that supports HTTP transport at your endpoint, for example `http://localhost:4000/mcp`. The configuration format depends on the client.
