---
title: File Storage
description: Store uploaded files in S3 or an S3-compatible store, kept per tenant, with keys Brick builds and short-lived download links.
---

`defineStorage` with the `s3()` driver declares a file storage. Like a [key-value storage](/docs/storage), it is a [dep](/docs/dependencies) of the services that use it. Every file belongs to a tenant, taken from the service's [`identity` hook](/docs/context#identity), and your code never builds or passes a storage key: `put` returns an id, and every other method takes that id.

```ts title="src/storage.ts"
import { defineStorage, s3 } from "@brickkit/core";

export const files = defineStorage({
  driver: s3({
    bucket: "crm-uploads",
    prefix: "files/",
    // A directory: store there instead of S3, for local development and tests.
    local: process.env.S3_BUCKET ? undefined : ".brick/files",
  }),
});
```

```ts title="src/services/crm/crm.service.ts"
import { defineService } from "@brickkit/core";
import { files } from "../../storage";

export const crm = defineService("crm", {
  database,
  deps: { files },
  context: async ({ request }) => ({ user: await readUser(request) }),
  identity: (ctx) => ctx.user && { id: ctx.user.id, tenant: ctx.user.orgId },
});
```

Accept an upload with [`t.File`](/docs/services-and-actions#file-uploads), with its limits on the field, and store it:

```ts title="src/services/crm/actions/attach-file.action.ts"
export const attach = crm.action({
  name: "attachFile",
  input: t.Object({
    file: t.File({
      maxSize: 10 * 1024 * 1024,
      accept: ["application/pdf", "image/*"],
    }),
    contactId: t.String(),
  }),
  authorize: ({ user }) => !!user,
  execute: async ({ input, ctx }) => {
    const stored = await ctx.deps.files.put(input.file); // Brick builds the key
    await ctx.db.insert(attachments).values({
      fileId: stored.id,
      contactId: input.contactId,
      name: input.file.name,
    });
    return { fileId: stored.id };
  },
});
```

Read it back, inside the caller's tenant:

```ts
const url = await ctx.deps.files.url(row.fileId, { download: row.name }); // short-lived signed GET
const blob = await ctx.deps.files.get(row.fileId); // server-side read
await ctx.deps.files.delete(row.fileId);
```

Keep the id in your database, next to the record the file belongs to, and check that the caller may see that record before you hand out a link.

## Methods

| Method                                 | Returns                     | Does                                                                                                                 |
| :------------------------------------- | :-------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| `put(file, { contentType? })`          | `{ id, size, contentType }` | Stores the `Blob` or `File` under a new id. `contentType` defaults to the file's own type, the one `t.File` checked. |
| `url(id, { expiresInMs?, download? })` | `string`                    | A signed GET, valid for 5 minutes by default, served as an attachment named `download`.                              |
| `get(id)`                              | `Blob \| undefined`         | The file, with its content type, or `undefined` when the tenant has no file with that id.                            |
| `delete(id)`                           | `void`                      | Removes the file; does nothing when the tenant has no file with that id.                                             |
| `in(tenant)`                           | the four methods above      | On the imported handle only: the files of one tenant, for code outside a request.                                    |

`ctx.deps.files` is typed from the driver: the first four methods, and none of a key-value storage's. It has no `in`: to name a tenant, import the handle, a deliberate act in server code, so an action cannot read another tenant's files with `ctx.deps.files.in(input.orgId)`.

## Tenants and keys

In S3, a file is stored at `<prefix><encodeURIComponent(tenant)>/<id>`, where the id is a `crypto.randomUUID()` Brick generates. In [local mode](#local-mode), the tenant's folder is instead the SHA-256 hex digest of the tenant, because disks may ignore case (`Acme` and `acme` would be one folder), drop a trailing dot, reserve names such as `CON` or cap a name's length. No method takes a key, a path or a URL.

Every method checks that the id is a UUID, then builds the key under the current tenant. So another tenant's id, a URL someone pasted, `../` or an encoded `/` resolves to a file that does not exist in the caller's own tenant: `get` returns `undefined`, `delete` does nothing, and `url` refuses an id that is not a UUID and, for another tenant's id, signs a link to nothing.

In a call, `ctx.deps.files` is scoped to the tenant of that call's identity. The tenant is resolved when a method is first called, so a call that never touches files never runs the `identity` hook. A call with no tenant (an anonymous caller, or an identity without `tenant`) throws; nothing falls back to an unscoped prefix. A service that has a file storage in its deps but no `identity` hook fails at startup.

Handing `ctx` to another service's action does not hand it your files: that service sees its own deps, as always.

A view kept from one call and used in another still acts as the first call's tenant, so don't keep `ctx.deps.files` beyond the call.

### Outside a request

A listener, a schedule or a webhook has no caller. Name the tenant:

```ts
import { files } from "../storage";

const blob = await files.in(event.payload.orgId).get(event.payload.fileId);
```

`in()` throws on an empty tenant, and on `.` and `..`. The handle's own methods (`files.get(id)` without `in`) throw, and say to use `in`.

## Credentials

`s3()` takes `bucket`, `prefix`, `local`, and the settings of Bun's built-in S3 client: `accessKeyId`, `secretAccessKey`, `sessionToken`, `region` and `endpoint`. Each of the last five is a string or a [`defineSecret`](/docs/reference/configuration#secrets-management-brickkitcore) reference. Any you leave out comes from Bun's environment variables: `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_SESSION_TOKEN`, `S3_REGION`, `S3_ENDPOINT`, `S3_BUCKET`, or their `AWS_*` equivalents.

```ts
import { defineSecret, defineStorage, s3 } from "@brickkit/core";

export const files = defineStorage({
  driver: s3({
    bucket: "crm-uploads",
    prefix: "files/",
    endpoint: "https://<account-id>.r2.cloudflarestorage.com", // R2, MinIO, any S3-compatible store
    accessKeyId: defineSecret("R2_ACCESS_KEY_ID"),
    secretAccessKey: defineSecret("R2_SECRET_ACCESS_KEY"),
  }),
});
```

Outside local mode a bucket is required, from `bucket`, `S3_BUCKET` or `AWS_BUCKET`: without one, `brick()` refuses to start for a storage among an app's deps, and a handle used on its own throws on its first call. The variables are read then, not at import.

Static keys, environment variables and a session token are supported. A credentials callback (to refresh IAM role credentials) is not.

Nothing connects and no credential is read when the module is imported: deps are created at import, and `brick info` and `brick gen` import the app without starting it. The client is created on the first call.

Give the credentials `s3:ListBucket` on the bucket as well as `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject`: without it, S3 answers a read of a missing file with 403 instead of 404, and `get` throws instead of returning `undefined`.

## Download links

`url()` returns a presigned GET that S3 serves with `Content-Disposition: attachment` and the `download` name, so a stored file is downloaded, never rendered inline from the storage origin. It is valid for 5 minutes unless you pass `expiresInMs`, at most 7 days (the most S3 accepts); a longer one throws, in both modes.

A signed URL is a bearer credential until it expires: anyone holding it can download the file. Don't log it. Brick's own errors never include one: when S3 cannot be reached, the error names only the operation.

## Local mode

With `local` set to a directory, files are written under it instead of S3, under the same prefix with the tenant's folder named by its digest (see [Tenants and keys](#tenants-and-keys)), with the same id and tenant checks and the same limits. Only the last write differs, so a test in local mode exercises the checks that matter. Nothing touches the directory until the first `put`.

`url()` then returns a link to `/_brick/files?token=…`, a route Brick mounts when an app has a file storage in local mode among its services' or plugins' deps. A storage used only through an imported handle's `in()`, in no app's deps, gives links that answer 403. The token is signed over the key, a digest of the directory (not its path) and an expiry, with a key generated per process, so links stop working when the process restarts. The route refuses an expired or altered token. Writing, reading and removing all require the file's folder to resolve, through symlinks, to that same folder under the directory, and the route never serves a symlinked file. Someone who can write inside the storage directory is trusted: a symlink planted there cannot make Brick write or read a file outside it, but a symlinked prefix folder can leave an empty tenant folder at its target, and a link swapped in between the check and the write is not guarded against. The token is in the query string because the request log and traces record only the path.

The link is relative to the app's origin. Brick warns once at startup when `local` is set and `NODE_ENV` is `production`.

## Upload limits

Declare the limits on the input field:

```ts
t.File({ maxSize: 10 * 1024 * 1024, accept: ["application/pdf", "image/*"] });
t.Files({ maxSize: 5 * 1024 * 1024, maxItems: 10, accept: ["image/*"] });
```

`accept` lists content types; `type/*` matches any subtype, `*/*` any type, and the match ignores case and parameters such as `charset`. A file over `maxSize` or of a type not listed fails input validation with `VALIDATION_FAILED` (400) before `execute` runs.

Over HTTP, the type checked is the one Bun derives from the extension of the part's file name. The part's own `Content-Type` is ignored: `a.pdf` sent as `text/html` arrives as `application/pdf`, and a part named `photo`, or a `Blob` appended without a name (sent as `blob`), arrives with an empty type, which no `accept` list but `*/*` matches. So a client must send a file name whose extension matches the type: `form.append("file", canvasBlob, "photo.png")`. A `.txt` file arrives as `text/plain;charset=utf-8`.

Both the name and the bytes come from the client: this is not content inspection, and a client can send any bytes as `photo.png`. `put` stores the type that was checked, and links are served as attachments, so a mislabeled file is downloaded, not rendered.

## Testing

Run tests against `local` with a temporary directory: they need no network and check the same tenant and id rules as S3. To replace the storage in a unit test, pass a fake in the call's deps; it is used as given:

```ts
await attach.execute({
  input: { file, contactId: "c1" },
  ctx: { deps: { files: fakeFiles } },
});
```

## Not covered

- Uploads straight from the browser to S3 with a presigned PUT: files pass through your action.
- Inspecting a file's bytes to find its real type.
- A credentials callback for IAM roles.
- A key namespace per service: services that share a storage share each tenant's files.
- Listing a tenant's files: keep the ids in your database.
- Image processing, rate limits on uploads, and an audit log of file access.
