title: Execution Context & Services
description: Resolve request context, inject databases and users, and isolate in-process service calls.

Execution context provides request metadata, database handles, logging, and user authentication state to actions and lifecycle hooks.

## Minimal Example

Configure a service context resolver to parse authentication headers and inject user identity into actions:

```ts title="src/services/billing.ts"
import { defineService, t } from "@brickkit/core";

// Define custom session shape
interface BillingUser {
  id: string;
  plan: "free" | "pro";
}

export const billingService = defineService("billing", {
  context: async (baseCtx): Promise<{ user: BillingUser | null }> => {
    const auth = baseCtx.request.headers.get("authorization");
    if (!auth) return { user: null };

    // Example token validation
    const user =
      auth === "Bearer pro-token"
        ? { id: "usr_42", plan: "pro" as const }
        : { id: "usr_10", plan: "free" as const };

    return { user };
  },
});

export const getSubscription = billingService.action({
  name: "getSubscription",
  output: t.Object({ plan: t.String() }),
  execute: ({ ctx, error }) => {
    // Error helpers throw; `return` lets TypeScript narrow `ctx.user`
    if (!ctx.user) return error.UNAUTHORIZED("Sign in required");
    return { plan: ctx.user.plan };
  },
});
```

## `BaseContext` Properties

Every action invocation and service resolver receives a `BaseContext` containing HTTP and runtime telemetry primitives:

| Field       | Type                      | Description                                                                                              |
| :---------- | :------------------------ | :------------------------------------------------------------------------------------------------------- |
| `request`   | `Request`                 | Web-standard `Request` for the active HTTP call, or a placeholder `http://localhost` request in-process. |
| `db`        | `TDb`                     | Database instance from the owning service's handle.                                                      |
| `logger`    | `Logger`                  | Logger with `.info()`, `.warn()`, `.error()`, and `.debug()`.                                            |
| `traceId`   | `string`                  | Trace ID. Over HTTP, taken from the `x-trace-id` header when present (e.g., `tr_k2l9p0`).                |
| `requestId` | `string`                  | Request ID. Over HTTP, taken from the `x-request-id` header when present (e.g., `req_k2l9p0`).           |
| `services`  | `Record<string, any>`     | Reserved. Brick passes an empty object; use `useService` to call other services.                         |
| `metadata`  | `Record<string, unknown>` | Over HTTP, `{ headers }` with the request headers; an empty object in-process.                           |

Over HTTP, Brick echoes `traceId` and `requestId` back as `x-trace-id` and `x-request-id` response headers.

## Service Context Resolvers

Brick passes `BaseContext` to the service's `context` resolver on every HTTP request and every in-process call:

```ts title="src/services/projects.ts"
export const projectsService = defineService("projects", {
  context: async (baseCtx) => {
    const tenantId = baseCtx.request.headers.get("x-tenant-id") ?? "default";
    baseCtx.logger.info(`Resolving context for tenant: ${tenantId}`);

    return {
      tenantId,
      resolvedAt: Date.now(),
    };
  },
});
```

The returned object is merged with `BaseContext` to form `ActionContext`. Inside `execute({ ctx })`, TypeScript infers both `BaseContext` properties (like `ctx.db` and `ctx.logger`) and the resolved properties (like `ctx.tenantId`).

## Identity

Brick doesn't own users, sessions or tenants: your `context` resolver puts whatever your auth gives you on `ctx`. Features that need to know who the caller is, and which tenant they act in, ask the service's `identity` hook:

```ts title="src/services/crm.ts"
export const crm = defineService("crm", {
  database,
  context: async ({ request }) => ({ user: await readUser(request) }),
  identity: (ctx) =>
    ctx.user && {
      id: ctx.user.id,
      label: ctx.user.email,
      tenant: ctx.user.orgId,
    },
});
```

The hook returns an `Identity`, or `null` or `undefined` for an anonymous caller. It may be async.

| Field    | Type     | Used as                                                             |
| :------- | :------- | :------------------------------------------------------------------ |
| `id`     | `string` | Who: the rate-limit key and the [audit log](/docs/audit-log) actor. |
| `label`  | `string` | Optional. A display name for the audit log.                         |
| `tenant` | `string` | Optional. Which tenant the caller acts in.                          |

`ctx` is the service's own context, typed from what `context` returns and from the service's [deps](/docs/dependencies). Brick keeps only `id`, `label` and `tenant` of what the hook returns, so returning a whole user object hands nothing else on; an empty `id` is an error. Brick treats the strings as opaque: it compares and stores them, never parses them.

The hook runs at most once per call, and only when a feature asks for the identity; a call that never needs it never runs it. A call is one HTTP request, socket connection or socket message, tool call or direct `action.execute`, together with the calls to the same service's actions it passes its `ctx` to. An in-process call to another service is a call of its own: it resolves that service's own `identity` against its own context.

The identity is resolved from `ctx` as it is the first time a feature asks, and stays fixed for the rest of the call, for copies of `ctx` too. Changing `ctx.user` on a copy, as in `inner.execute({ ctx: { ...ctx, user: admin } })`, changes what the action reads, not who the call is.

The [audit log](/docs/audit-log) stores `id`, `label` and `tenant` of every change it records, as the hook returned them, and requires the hook: a service whose database holds an audit table fails when it is built without one.

If your resolver already sets `tenantId`, which Brick forwards between services but never sets itself, return it: `tenant: ctx.tenantId`. Validate it first, as for any envelope field.

## Context Isolation Across In-Process Service Calls

When calling another service in-process with `useService`, Brick enforces strict context isolation:

```ts title="src/services/notifications.ts"
import { defineService, useService } from "@brickkit/core";
import { usersService } from "./users";

export const notificationsService = defineService("notifications");

// Typed from the users service's actions (through the generated contract).
// `from` identifies the calling service, so `users` actions see `ctx.caller === "notifications"`.
const users = useService(usersService, { from: "notifications" });

export const sendWelcome = notificationsService.action({
  name: "sendWelcome",
  execute: async ({ ctx }) => {
    // Methods take (input, callCtx?) and run the action in-process
    const user = await users.getUser({ id: "usr_1" });
    ctx.logger.info(`Sending welcome email to ${user.email}`);
    return { sent: true };
  },
});
```

Each method takes the action's input as its first argument and an optional call context as its second. Only in-process dispatch is implemented. See [Service references](/docs/dependencies#service-references) for how the types are inferred.

Besides its context, each service has its own [dependencies](/docs/dependencies) in `ctx.deps`. A call to another service runs with that service's deps, never the caller's.

### Security Boundaries

What the receiving service sees:

1. **Own context and database**: The receiving service runs its own `context` resolver and uses its own database.
2. **Framework fields are dropped**: `db`, `request`, `logger`, `services`, and `metadata` in the call context are discarded before reaching the receiving service.
3. **Envelope fields pass through**: Only `caller`, `user`, `traceId`, `requestId`, `tenantId`, and `dashboard` are forwarded. Passing `ctx` on lets a `dashboard: true` action be called from a dashboard request's action. The resolver receives these fields and its returned values always take precedence. Caller custom fields such as `session` and `isOwner` are discarded for direct action calls and proxy calls. Treat `tenantId` as a claim to validate, not proof of access.
4. **`ctx.caller`**: The client sets `ctx.caller` to `from` — the name you passed when creating it, `useService(usersService, { from: "notifications" })` — never the target service's name. When `from` is provided, any `caller` in the client's `options.context` or the per-call context is ignored, so it cannot be spoofed. Without `from`, an explicitly supplied `caller` still passes through; otherwise `caller` is left unset.

### Internal calls without cookies

A `useService` call receives a placeholder request without browser cookies. A resolver that supports internal callers should validate `envelope.user` and derive its own session and helpers. For example, accept a user ID only after checking it with your identity store and caller trust policy:

```ts
const accounts = defineService("accounts", {
  context: async (envelope) => {
    const claim = envelope.user;
    const userId =
      typeof claim === "object" &&
      claim !== null &&
      "id" in claim &&
      typeof claim.id === "string"
        ? claim.id
        : undefined;
    // Application functions validate the caller and load an allowed identity.
    const user =
      userId && isTrustedCaller(envelope.caller)
        ? await loadAllowedUser(userId, envelope.tenantId)
        : null;
    return {
      user,
      session: null,
      isOwner: (ownerId: string) => user?.id === ownerId,
    };
  },
});
```

For HTTP calls, continue resolving identity from the actual request's authentication headers or cookies. Passing `{ user }` directly cannot replace a resolver's returned `user`, even when the resolver returns `null`. Tests should provide a request or configure a resolver that explicitly validates the internal envelope.
