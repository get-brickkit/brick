This is optional: an app with only TypeScript services needs none of it, and nothing on this page changes how it runs.

A Brick app can have services written in Go or Rust next to its TypeScript ones. Each runs as its own process. Use one for an action that needs a Go or Rust library, or a hot path. Keep everything else in TypeScript.

## What a Go or Rust service can do

A Go or Rust service has actions, and nothing else: no events, outbox, listeners, workflows, commands, sockets, CRUD or plugins. Its actions can:

- read and write the app's Postgres database, with `pgx` in Go or `sqlx` in Rust. The TypeScript side owns the schema and the migrations.
- return the errors they declare, with the same error envelope a TypeScript action returns.
- read the signed-in user from the caller's Better Auth JWT.
- call any other service's actions, in any language, with a generated client.

## Install

The SDKs are released with the `@brickkit` npm packages, under the same version. Use the version of your `@brickkit/core`, 0.13.0 or later.

Go, in the service's module:

```sh
go get github.com/get-brickkit/brick/sdk/go@v0.13.0
```

The package to import is `github.com/get-brickkit/brick/sdk/go/brick`. The module is tagged `sdk/go/v0.13.0` in the Brick repository. It needs Go 1.26.3 or later.

Rust, in the service's crate:

```sh
cargo add brickkit@0.13.0 schemars serde tokio --features serde/derive,tokio/macros,tokio/rt-multi-thread
```

The crate is [`brickkit`](https://crates.io/crates/brickkit), imported as `brickkit`. It needs Rust 1.88 or later.

## Development and production

In development, `brick dev` keeps one port. Bun serves the pages, the TypeScript services and `/api/auth/*`, and forwards `/api/<go-or-rust-service>/*` to that service's process:

```txt
browser ──► Bun :5174 ──► /api/billing/*  ──► Go    127.0.0.1:<port>
                     └──► everything else (TS services, pages, /api/auth/*)
```

In production, a hop through Bun costs about 0.15 ms per request, which is most of what Go or Rust saves. So a reverse proxy routes by path, and browsers reach each Go or Rust process directly:

```txt
browser ──► proxy :443 ──► /api/billing/*  ──► Go    billing:4001
                      ├──► /api/fx/*       ──► Rust  fx:4002
                      └──► everything else ──► Bun   app:3000
```

`brick build --deploy` writes that proxy's config, and the rest of the deployment. See [Deploy](#deploy).

Either way, the Go or Rust service does what Bun does for a TypeScript request:

- it reads the user from the `Authorization: Bearer` JWT, and checks it against the app's JWKS.
- it keeps the request's `x-request-id`, or makes one, and returns it.
- it continues the W3C `traceparent`, or starts a trace, and returns `x-trace-id`.
- it answers CORS from the origins of `brick({ cors })`.

It serves each action at `POST /api/<service>/<action>`, so the proxy forwards paths unchanged, and at `POST /<action>` for other services.

## Sign-in: Better Auth JWTs

A Go or Rust service checks the caller itself, with the [Better Auth JWT plugin](https://www.better-auth.com/docs/plugins/jwt). You only need it when the app has Go or Rust services. TypeScript services keep reading the session cookie in their `context` hook.

Add the plugin to the app's Better Auth instance:

```ts title="src/auth.ts"
import { betterAuth } from "better-auth";
import { jwt } from "better-auth/plugins";

export const auth = betterAuth({
  baseURL: process.env.BASE_URL,
  plugins: [jwt()],
});
```

It signs tokens with an Ed25519 key, publishes the public keys at `/api/auth/jwks`, and gives a signed-in browser a token in two ways:

- `GET /api/auth/token` answers `{ "token": "..." }`.
- `getSession` returns it in the `set-auth-jwt` response header.

The browser sends it to the Go or Rust service as `Authorization: Bearer <token>`. A token lasts 15 minutes, so get a new one before it expires. Better Auth doesn't put this token in a cookie, so the services read only the header.

Tell each Go or Rust service where to find the keys:

| Variable             | Value                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `BRICK_JWT_ISSUER`   | Better Auth's `baseURL`, which it signs as `iss`. Without it, the service reads no JWTs. |
| `BRICK_JWT_AUDIENCE` | The `aud` to expect. Default: the issuer, as Better Auth signs it.                       |
| `BRICK_JWKS_URL`     | Default: `<issuer>/api/auth/jwks`. In a container, the Bun app's internal address.       |

The service checks the signature, `exp`, `iss` and `aud`. It caches the keys. A token signed with a key it doesn't have makes it fetch them again, at most every 10 seconds, so Better Auth can rotate keys. It also refetches every 10 minutes.

The user is the token's claims without the registered ones (`iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`). Better Auth signs the session's user, so a Go or Rust action sees the same `id`, `email`, `name` and other fields a TypeScript action sees in `ctx.user`. With no valid token, the call has no user. An action that needs one returns the same 401 a TypeScript action's `authorize` returns:

```json
{
  "name": "ActionExecutionError",
  "code": "UNAUTHORIZED",
  "message": "Access denied for action 'charge'",
  "status": 401,
  "requestId": "req_3"
}
```

## Calls between services

Services call each other directly, not through Bun or the proxy. A call carries the internal token in `x-brick-internal`, and the caller's user, tenant and own name in `x-brick-user`, `x-brick-tenant` and `x-brick-caller`.

A service trusts `x-brick-*` headers only with the internal token. A request without the token is a public call: its `x-brick-*` headers are ignored and its user comes from its JWT. A request with a wrong token gets a 401. The Caddy, nginx and Traefik configs that `brick build --deploy` writes also remove `x-brick-*` from incoming requests. The Kubernetes Ingress can't; see [Deploy](#deploy).

The original JWT is not forwarded. Many callers don't have one: a TypeScript action that read the session cookie, or a background job. A JWT can also expire in the middle of a chain of calls. The internal token never reaches a browser, and only services that hold it can name a user.

Each process gets these variables. `brick dev` and `brick start` set them; the deploy targets write them:

| Variable               | Value                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| `BRICK_SERVICES`       | JSON: each service's name and base URL, the TypeScript services included                       |
| `BRICK_INTERNAL_TOKEN` | The shared secret: yours in production, else random for each `brick dev` or `brick start` run. |
| `BRICK_PORT`           | The port to listen on                                                                          |
| `BRICK_HOST`           | The address to listen on. Default `127.0.0.1`; `0.0.0.0` in a container.                       |
| `BRICK_PREFIX`         | The app's API prefix. Default `/api`.                                                          |
| `BRICK_CORS`           | The origins of `brick({ cors })` as JSON. A predicate origin isn't passed on.                  |

## Declare the service in the app

```ts title="src/app.ts"
import { brick, remoteService } from "@brickkit/core";
import { orders } from "./services/orders";

export const billing = remoteService({
  name: "billing",
  dir: "services/billing",
  dev: "go run .",
  build: { command: "go build -o bin/billing .", run: "./bin/billing" },
});

export default brick({ services: [orders], remote: [billing] });
```

| Option  | Meaning                                                                                                     |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| `name`  | The service name. It must match the name in the Go or Rust code.                                            |
| `dir`   | The Go module or Cargo crate, relative to the working directory.                                            |
| `dev`   | What `brick dev` runs in `dir`: `go run .` or `cargo run -q`.                                               |
| `build` | `command` builds the release binary (`brick build`), `run` starts it (`brick start`).                       |
| `port`  | A fixed port. Without one, a free port is picked at start, and the deploy targets use 4001, 4002 and so on. |

## Write it in Go

The Go SDK is `github.com/get-brickkit/brick/sdk/go/brick`. It uses chi for routing, Huma for the schemas and `lestrrat-go/jwx` for JWTs. Struct tags such as `minLength`, `maximum` and `enum` describe the input.

Create the module next to the app:

```sh
mkdir -p services/billing && cd services/billing
go mod init example.com/app/billing
go get github.com/get-brickkit/brick/sdk/go@v0.13.0
```

```go title="services/billing/main.go"
package main

import (
	"log"

	"github.com/get-brickkit/brick/sdk/go/brick"
)

type Charge struct {
	OrderID string `json:"orderId" minLength:"1"`
	Cents   int64  `json:"cents" minimum:"1" maximum:"100000"`
}

type Receipt struct {
	ID string `json:"id"`
}

func main() {
	svc := brick.NewService("billing")
	declined := svc.DefineError("CARD_DECLINED", 402, "The card was declined")

	brick.Action(svc, "charge", func(ctx *brick.Ctx, in Charge) (Receipt, error) {
		var user struct {
			ID string `json:"id"`
		}
		if err := ctx.RequireUser(&user); err != nil {
			return Receipt{}, err // the 401
		}
		if in.Cents > 50_000 {
			return Receipt{}, declined.New(nil)
		}
		log.Printf("charge for %s, request %s", user.ID, ctx.RequestID())
		return Receipt{ID: "r_1"}, nil
	})

	log.Fatal(svc.Serve())
}
```

`*brick.Ctx` is a `context.Context`. Pass it to `pgx` and to the generated client. It has `RequestID()`, `TraceID()`, `Caller()` (the calling service, or `""` for a call from outside), `TenantID()`, `User(&v)`, which reports whether there is a user, and `RequireUser(&v)`.

## Write it in Rust

The Rust crate is `brickkit`. It uses axum, serde, schemars for the schemas, `jsonschema`, reqwest with rustls, and `jsonwebtoken`. schemars attributes describe the input.

Create the crate next to the app:

```sh
cargo new --vcs none services/billing && cd services/billing
cargo add brickkit@0.13.0 schemars serde tokio --features serde/derive,tokio/macros,tokio/rt-multi-thread
```

The same `billing` service as in Go:

```rust title="services/billing/src/main.rs"
use brickkit::{Ctx, Error, ErrorDef, Service};
use schemars::JsonSchema;
use serde::{Deserialize, Serialize};

const DECLINED: ErrorDef = ErrorDef::new("CARD_DECLINED", 402, "The card was declined");

#[derive(Deserialize, JsonSchema)]
struct Charge {
    #[serde(rename = "orderId")]
    #[schemars(length(min = 1))]
    order_id: String,
    #[schemars(range(min = 1, max = 100000))]
    cents: i64,
}

#[derive(Deserialize)]
struct User { id: String }

#[derive(Serialize, JsonSchema)]
struct Receipt { id: String }

#[tokio::main]
async fn main() -> std::io::Result<()> {
    Service::new("billing")
        .error(DECLINED)
        .action("charge", |ctx: Ctx, input: Charge| async move {
            let user: User = ctx.require_user()?; // the 401
            if input.cents > 50_000 {
                return Err(DECLINED.err());
            }
            Ok::<_, Error>(Receipt { id: format!("r_{}", user.id) })
        })
        .serve()
        .await
}
```

`Ctx` has `request_id()`, `trace_id()`, `caller()`, `tenant_id()`, `user::<T>()` (an `Option`) and `require_user::<T>()`. Any other error, such as an `sqlx::Error` returned with `?`, is logged and answered as a 500.

Both SDKs fetch the JWKS over HTTP or HTTPS, and check HTTPS certificates against the system's roots. In a container, that needs the CA certificates, which the generated Dockerfiles copy. Pointing `BRICK_JWKS_URL` at the Bun app's internal address, as the deploy targets do, skips TLS and the public network.

## Validation and errors

Each service validates its own input. The Go and Rust SDKs report problems with the same messages, paths and order as TypeBox. The same bad input gives the same bytes from every language:

```json
{
  "name": "ValidationError",
  "code": "VALIDATION_FAILED",
  "message": "Validation failed for action 'charge' input",
  "status": 400,
  "errors": [
    {
      "path": "/cents",
      "message": "Expected integer to be less or equal to 100000",
      "value": 250000
    }
  ],
  "requestId": "req_3"
}
```

A declared error has `name`, `code`, `message`, `status`, `details` and `requestId`, as in TypeScript. When a TypeScript action calls a Go or Rust action that fails, it gets an `ActionExecutionError` with the same `code`, `status` and `details`.

The SDKs match TypeBox for `type`, `required`, `properties`, `additionalProperties`, `enum`, `const`, `anyOf`, string length and `pattern`, number bounds and `multipleOf`, and array `items` and length. String formats aren't checked. Huma marks Go structs `additionalProperties: false`, so a Go action rejects unknown fields; add a `_ struct{} additionalProperties:"true"` field to allow them.

## Call another service

From TypeScript, `useService` works as it does for a TypeScript service. The call goes straight to the child:

```ts
const billing = useService(billingService, { from: "orders" });
const receipt = await billing.charge(
  { orderId, cents: 500 },
  { user: ctx.user, requestId: ctx.requestId },
);
```

`billingService` is what `remoteService` returned. Go and Rust call other services through a generated client, which forwards the user, request id and trace of the current call, with their own service as the caller:

```go
receipt, err := brickclient.BillingCharge(ctx, brickclient.BillingChargeInput{OrderId: "o1", Cents: 500})
```

```rust
let receipt = brick_client::billing_charge(&ctx, &input).await?;
```

A Go or Rust service calls a TypeScript action at `POST /_brick/call/<service>/<action>` on the Bun app. That route runs the action's validation and authorization. It serves only requests with the internal token. The action's context hook receives the caller's user as `ctx.user`, so keep it: `context: ({ request, user }) => ({ user: user ?? fromCookie(request) })`.

## Generate the contract and the clients

```sh
brick gen contract src/app.ts
```

`brick gen` runs each Go and Rust service's `dev` command with `BRICK_MANIFEST=1` (a built binary also takes `--brick-manifest`). Each prints its name, its actions with their input and output JSON Schema, and its errors. `brick gen` merges them with the TypeScript services into `_brick/contract.json`. Then it writes:

- the TypeScript contract (`_brick/contract.ts`), so the typed client and `useService` know the Go and Rust actions.
- `brickclient/client.go` in each Go service.
- `src/brick_client.rs` in each Rust service. Add `mod brick_client;`.

The generated clients import the published SDKs: `github.com/get-brickkit/brick/sdk/go/brick` and `brickkit`. Commit them. Rerun `brick gen` after changing an action's types in any language. In an app with a `brick.config.ts`, a bare `brick gen` does this too.

## Run it

| Command       | What it does                                                                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `brick dev`   | Runs each service's `dev` command next to the app. It restarts a service when a file in its `dir` changes, and only that service. The Vite plugin does the same. |
| `brick build` | Runs each `build.command`. With `--deploy`, also writes the production routing.                                                                                  |
| `brick start` | Starts each `build.run` binary, then the app, on one host. Put one of the generated proxies in front to skip the Bun hop.                                        |

Set `BRICK_JWT_ISSUER` in the app's environment (a `.env` file works): the services inherit it in `brick dev` and `brick start`.

With Vite's `server.https`, the services call TypeScript services at `https://localhost:<port>`, so their HTTP clients must trust the dev certificate. A self-signed one fails: use a locally trusted one such as mkcert's.

To run the binaries yourself, call `startRemoteServices(services, { mode: "start", appUrl, services: tsServiceNames, env: remoteEnv(app.definition) })` from `@brickkit/core` before the app starts, where `tsServiceNames` lists the TypeScript services' names so the Go and Rust services can call them. It sets `BRICK_SERVICES` and `BRICK_INTERNAL_TOKEN` in the process, so start the app from the same process or pass them on.

## Deploy

`brick build --deploy` writes every deploy target from one routing table: `/api/<service>/` to each Go or Rust process, and everything else to Bun.

```sh
brick build --deploy caddy,compose --domain app.example.com
```

Or set it in `brick.config.ts`, and a plain `brick build` writes it:

```ts title="brick.config.ts"
import { defineConfig } from "@brickkit/cli";

export default defineConfig({
  deploy: {
    targets: ["caddy", "compose"],
    domain: "app.example.com",
    // The Bun app in compose and Kubernetes. These are the defaults.
    app: {
      build: "bun x brick build",
      start: "bun dist/brick/server.js",
      port: 3000,
    },
  },
});
```

The flags win over the config. Nothing is written unless you ask for a target. An app without Go or Rust services can ask too, and gets a proxy that sends everything to Bun.

| Target       | Files in `deploy/`                               | What it is                                                                                                         |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `caddy`      | `caddy/Caddyfile`                                | Caddy, with a keep-alive pool of 256 per process. With `--domain`, automatic HTTPS.                                |
| `nginx`      | `nginx/nginx.conf`                               | A full `nginx.conf` with a keep-alive upstream per process. Terminate TLS in front of it, or add your certificate. |
| `traefik`    | `traefik/traefik.yml`, `traefik/dynamic.yml`     | Static config, and the routes for Traefik's file provider. With `--domain`, Let's Encrypt.                         |
| `kubernetes` | `kubernetes/brick.yaml`                          | A Deployment and a Service per process, and an Ingress routing by path. With `--domain`, TLS from `brick-tls`.     |
| `compose`    | `compose/compose.yaml`, a Dockerfile per process | Bun, each Go and Rust service, and the proxy: the first of caddy, nginx or traefik you named, else Caddy.          |
| `routes`     | `routes/routes.json`                             | The routing table itself, for a cloud load balancer or your own setup.                                             |

The Caddyfile, for an app with a Go service `billing` and a Rust service `fxRates`:

```txt title="deploy/caddy/Caddyfile"
app.example.com {
	request_header -X-Brick-Internal
	request_header -X-Brick-User
	request_header -X-Brick-Caller
	request_header -X-Brick-Tenant

	handle /api/billing/* {
		reverse_proxy billing:4001 {
			transport http {
				keepalive_idle_conns_per_host 256
			}
		}
	}

	handle /api/fx-rates/* {
		reverse_proxy fx-rates:4002 {
			transport http {
				keepalive_idle_conns_per_host 256
			}
		}
	}

	handle {
		reverse_proxy app:3000 {
			transport http {
				keepalive_idle_conns_per_host 256
			}
		}
	}
}
```

The nginx routes:

```txt title="deploy/nginx/nginx.conf"
    upstream billing {
        server billing:4001;
        keepalive 256;
    }

        location /api/billing/ {
            proxy_pass http://billing;
        }

        location / {
            proxy_pass http://app;
        }
```

The Traefik routers:

```yaml title="deploy/traefik/dynamic.yml"
http:
  routers:
    billing:
      rule: "Host(`app.example.com`) && PathPrefix(`/api/billing/`)"
      service: billing
      entryPoints: [websecure]
      middlewares: [strip-brick-headers]
      priority: 3
      tls:
        certResolver: brick
```

The Kubernetes Ingress:

```yaml title="deploy/kubernetes/brick.yaml"
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: brick
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api/billing/
            pathType: Prefix
            backend:
              service:
                name: billing
                port: { number: 4001 }
```

Create the internal token before you apply it. Without `--domain` the manifest doesn't know your public URL, so the services read `BRICK_JWT_ISSUER` from the same Secret:

```sh
kubectl create secret generic brick --from-literal=BRICK_INTERNAL_TOKEN=$(openssl rand -hex 24) \
  --from-literal=BRICK_JWT_ISSUER=https://app.example.com
kubectl apply -f deploy/kubernetes/brick.yaml
```

The images are `<name>:latest` with `imagePullPolicy: IfNotPresent`: load them into the cluster (`kind load docker-image`, `minikube image load`) or tag and push them to your registry and edit `image`.

An Ingress can't remove request headers in a portable way, so the generated one doesn't, and `x-brick-*` from a browser reaches the services. The guard on Kubernetes is the services' own rule, which every SDK and the Bun app apply and test: without the internal token they ignore `x-brick-*`, and with a wrong one they answer 401. Only a request that carries `BRICK_INTERNAL_TOKEN` can name a user, tenant or caller, so keep the token in the Secret and out of the browser. To strip the headers at the edge too, route with the Gateway API instead of the Ingress: an `HTTPRoute` filter of type `RequestHeaderModifier` with `remove: [X-Brick-Internal, X-Brick-User, X-Brick-Caller, X-Brick-Tenant]`. ingress-nginx's `configuration-snippet` annotation could do it, but most clusters disable snippets, so `brick build --deploy` doesn't rely on it.

With compose, put the token and the public URL in `deploy/compose/.env`. Compose refuses to start without the token:

```sh title="deploy/compose/.env"
BRICK_INTERNAL_TOKEN=<openssl rand -hex 24>
BRICK_JWT_ISSUER=https://app.example.com
```

```sh
docker compose -f deploy/compose/compose.yaml up --build
```

Each Go or Rust Dockerfile copies only the service's folder and its local dependencies, builds the release binary, and runs it on `debian:trixie-slim`. A service that depends on the published SDK builds from the project root. When `go.mod` has a `replace` or `Cargo.toml` a `path` dependency that points outside the project, as in a monorepo, the build context becomes the closest folder that holds both, and `compose.yaml` says so. Each Dockerfile has a `.dockerignore` next to it that leaves out `target/`, `node_modules/` and `.git/` (for the Bun app, `node_modules/`, `.git/`, `dist/` and `deploy/`). Each process gets `BRICK_SERVICES` with the other processes' compose or Kubernetes addresses, and each Go or Rust service gets `BRICK_JWKS_URL=http://app:3000/api/auth/jwks`.

`routes.json` lists the same routes, the upstreams with their addresses, languages and environment, and the headers to strip:

```json title="deploy/routes/routes.json"
{
  "stripHeaders": [
    "X-Brick-Internal",
    "X-Brick-User",
    "X-Brick-Caller",
    "X-Brick-Tenant"
  ],
  "routes": [
    { "path": "/api/billing/", "upstream": "billing" },
    { "path": "/api/fx-rates/", "upstream": "fx-rates" },
    { "path": "/", "upstream": "app" }
  ]
}
```

## Measure it

The pages example has the same three APIs in TypeScript, Go and Rust: `echo`, `validate` and `db` (one `SELECT` by id, with a pool of 10 connections in each language). Its Go and Rust services are only registered with `BRICK_BENCH=1`, so the example runs without Go or Rust. The benchmark sets it, builds everything for production, starts Caddy in docker with the generated Caddyfile, and calls every API 200 times, one request at a time, by three paths:

| Path      | Route                                                                  |
| --------- | ---------------------------------------------------------------------- |
| `proxy`   | client → Caddy → the service. The production path, for TypeScript too. |
| `direct`  | client → the service's own port.                                       |
| `gateway` | client → Bun → Go or Rust. The `brick dev` path, for comparison.       |

```sh
bun run --cwd examples/pages bench
BENCH_CADDY_BIN=/path/to/caddy bun run --cwd examples/pages bench   # adds proxy-native
```

On macOS, docker's network adds its own overhead to the `proxy` path. Set `BENCH_CADDY_BIN` to a Caddy binary to also measure `proxy-native`, the same Caddyfile on the host.

It writes p50, p90, p99, mean, min and max for each language, API and path to `examples/pages/bench/results.json`.

The `load` mode measures throughput under concurrency. Through the native Caddy, it gives each language and API a 10 s warm-up, then 20 s measured with [oha](https://github.com/hatoo/oha) at 64 connections. It records requests per second, p50 and p99, and the CPU and peak memory of Caddy, Bun, Go and Rust, sampled with `ps`, into `examples/pages/bench/results-load.json`:

```sh
BENCH_CADDY_BIN=/path/to/caddy BENCH_OHA_BIN=/path/to/oha bun run --cwd examples/pages bench load
```

## Limits

- It is experimental. Pin the SDKs to the version of your `@brickkit/core` and read the release notes before you upgrade.
- A Go or Rust service has actions only: no events, outbox, listeners, workflows, commands, sockets, CRUD or plugins.
- It reads the user only from a Better Auth JWT in `Authorization`, not from the session cookie, and only when `BRICK_JWT_ISSUER` is set.
- Input validation matches TypeBox for the keywords listed above. String formats such as `email` or `uuid` aren't checked.
- The services run on macOS and Linux, not Windows.
- `brick dev` starts the services the app had at its first start. Restart it after adding one.
- Kubernetes doesn't strip `x-brick-*` at the Ingress. The internal token is the guard there, as described above.
