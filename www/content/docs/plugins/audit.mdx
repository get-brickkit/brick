---
title: Change History Plugin Recipe
description: Keep the values an update wrote in a table of your own, in the write's transaction, and tie them to the built-in audit log by trace id.
---

Brick's built-in [audit log](/docs/audit-log) records who changed which record, and when. It deliberately copies no values: a log that held them would be a second copy of your data without its access rules. Use it for the question "who changed this".

Some apps also need "what did it change". This recipe keeps that, in a table you can protect, prune and expose separately from the audit log. It builds a plugin with `definePlugin` that owns its table and subscribes to the host resource's updates, so installing it is one line.

The plugin does not record the actor. The audit log already does, by the service's `identity` hook, and the two rows of one call share a `trace_id`.

## The plugin

```ts title="src/plugins/history/index.ts"
import { definePlugin } from "@brickkit/core";

export const history = definePlugin({
  name: "@acme/brick-history",
  brick: "^0.11.0",
  requires: ["@brickkit/crud"],

  // Created in the host's database as <resource>_history.
  tables: ({ table, text, timestamp, json }) => ({
    history: table("history", {
      id: text("id")
        .primaryKey()
        .$defaultFn(() => crypto.randomUUID()),
      recordId: text("record_id").notNull(),
      changes: json("changes").notNull(), // the fields as this hook saw them
      traceId: text("trace_id").notNull(),
      at: timestamp("at")
        .notNull()
        .$defaultFn(() => new Date()),
    }),
  }),

  resource: ({ tables, hooks }) => {
    // Inside the write's transaction: the row commits or rolls back with it.
    hooks.beforeUpdate(async ({ id, data, ctx, tx }) => {
      // A copy: `data` is what the update writes, so deleting from it would drop the field from the write.
      const { password: _password, ...changes } = data;
      await tx.insert(tables.history).values({
        recordId: String(id),
        changes,
        traceId: ctx.traceId,
      });
    });
    return { history: tables.history };
  },
});
```

## Installing it

```ts title="src/services/accounts.ts"
import { crud } from "@brickkit/crud";
import { history } from "../plugins/history";

export const account = accountsService
  .resource({ name: "account", table: accountsTable, id: accountsTable.id })
  .use(
    crud({
      access: { authorize: ({ ctx }) => !!ctx.user },
      fields: {
        id: { read: true },
        name: { read: true, create: true, update: true },
      },
    }),
  )
  .use(history());
```

Every update through `account`'s CRUD routes, its bulk routes and in-process calls now writes a row to `account_history`. `account.history` is the table. `history` must come after `crud()`: `requires` refuses it otherwise.

To keep the history of every resource of a service, give the plugin a `service` part with the same hook and install it with `service.use(history())`: hooks on a service see the writes of all its resources.

## Reading the two together

The audit log says who and when; the history says what. Join them on the trace and the record:

```ts
const changes = await db
  .select({
    id: account.history.id,
    at: account.history.at,
    actor: auditLog.actorId,
    changes: account.history.changes,
  })
  .from(auditLog)
  .innerJoin(
    account.history,
    and(
      eq(auditLog.traceId, account.history.traceId),
      eq(auditLog.recordId, account.history.recordId),
    ),
  )
  .where(eq(auditLog.action, "account.update"))
  .orderBy(account.history.at);
```

One trace can update the same record more than once, for example a `bulkUpdate` with the same id twice. Each audit row of the record then matches each of its history rows, so the join repeats every change. Keep one row per history `id`, and order by the history row's own `at`.

## Considerations

- **Atomic writes**: the hook runs inside the write's transaction and writes through `tx`, so a history row exists exactly when its write committed. A hook that throws rolls the write back. Side effects outside the database belong in `hooks.afterCommit`.
- **The values are data**: they can include anything the update wrote. Do not copy passwords, payment details or personal data into the table, and give it the access rules of the table it describes. Leave such fields out of the copy you insert, as the example does with `password`; never delete them from `data`, which is what the update writes.
- **When it looks**: the row holds `data` as it stood when this hook ran. Hooks that run after it (plugins installed later, hooks of the service) can still add fields to the write, and the row does not show them. Install `history()` after the plugins that change `data`; hooks of the service always run after those of the resource.
- **Reading it**: expose `history` through a separate resource with restricted access, not through the resource it describes.
- **Append-only**: the [audit log's triggers](/docs/audit-log#making-it-append-only) work on this table too, with its name in place of `brick_audit`.
